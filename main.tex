\section{Higher-order goal \BvrHint{\ldots secondary framing}}
This project aims to reduce the time and effort required to plan a personalized trip by bringing itinerary planning, weather information, accommodation recommendations, maps, packing assistance, safety information, and collaborative planning into a unified platform. While the topic is broader than any single travel destination, the immediate engineering objective is to translate efficient and personalized travel planning into a measurable, deployable software solution.

\section{Time-to-value \BvrHint{\ldots primary heuristic}}
\begin{itemize}
\item We will deliver meaningful increments quickly by prototyping the core trip creation and itinerary workflow and validating it with users within a short iteration window.
\item We will prioritize fast feedback over perfection by using weekly iterations and targeting CI-backed automation early to reduce release friction.
\item We will first establish the core trip planner and then integrate weather, AI itinerary generation, packing, map, stay, safety, and collaboration features incrementally.
\item Success is defined by what can be delivered and measured in the first iteration, then improved based on user feedback.
\end{itemize}

\section{Problem Statement}
Travellers often need to gather and combine information from multiple sources, including maps, weather services, accommodation platforms, travel guides, and recommendation websites. Common pain points include:
\begin{itemize}
\item \textbf{Fragmentation:} trip information is distributed across multiple applications and websites, making it difficult to maintain a single coherent travel plan.
\item \textbf{Generic recommendations:} existing travel recommendations may not sufficiently account for individual interests, budget, travel style, trip duration, weather, and planned activities.
\item \textbf{Manual itinerary planning:} travellers often need to research attractions, estimate suitable timings, and manually arrange activities into a practical day-by-day schedule.
\item \textbf{Dynamic conditions:} weather can affect the suitability of outdoor activities and what travellers need to pack, but this information is often handled separately from itinerary planning.
\item \textbf{Packing uncertainty:} generic packing lists do not necessarily account for destination, weather, duration, and planned activities.
\item \textbf{Group coordination:} travelling with friends or family introduces additional difficulty because participants need to share information and coordinate changes to the itinerary.
\item \textbf{Information overload:} travellers may spend considerable time comparing accommodation, attractions, weather conditions, and activities before arriving at a final plan.
\end{itemize}

\textbf{Why this matters now (contextual relevance):} As travel planning involves increasingly large amounts of online information, an integrated system can reduce repetitive searching and provide a more structured and personalized planning workflow.

\section{Proposed Solution \BvrHint{\ldots Software Proposition}}
\subsection{Overview}
Build a web-based ``ItiNova'' system with the following components:
\begin{itemize}
\item \textbf{Trip planner:} users enter destination, travel dates or duration, number of travellers, budget, interests, and travel style. The system creates a basic day-by-day trip plan that users can edit, delete, and reorder.
\item \textbf{Weather and best-time recommendations:} the system provides destination-specific weather information for the selected dates, indicates general travel suitability, and provides simple weather-based recommendations.
\item \textbf{Hotel/stay recommendations:} users can discover and compare suitable stays based on budget, rating, type, and location, save preferred options, and open an external booking source. The platform will not handle hotel bookings.
\item \textbf{Smart packing assistant:} the system generates a personalized checklist using destination, weather, trip duration, and planned activities. Users can mark items as packed and modify the checklist.
\item \textbf{Travel health and safety:} the system provides general destination-specific health precautions, safety information, a travel safety checklist, emergency information, and useful medical-facility information where reliable data is available. It is not intended for diagnosis.
\item \textbf{Interactive travel map:} the map displays saved places, itinerary locations, and hotel locations. Users can open directions and add places to their itinerary.
\item \textbf{AI itinerary generator:} an AI module generates a structured day-by-day itinerary based on destination, dates, budget, interests, weather, and travel preferences. Users can request changes to the generated itinerary.

\end{itemize}

\subsection{Core workflow}
\begin{enumerate}
\item User creates an account and enters destination, travel dates or duration, number of travellers, budget, interests, and preferred travel style.
\item The system creates a basic trip plan around the selected destination and duration.
\item The system retrieves relevant weather information and presents travel suitability and simple weather-based recommendations.
\item The AI module can generate a more detailed structured itinerary using destination, dates, budget, interests, weather, and preferences.
\item The user reviews and modifies the itinerary by adding, removing, editing, or reordering activities.
\item The packing assistant generates a checklist based on destination, weather, duration, and planned activities.
\item Users can view itinerary locations, saved places, and stay locations on an interactive map.
\item Users can explore suitable stays based on their preferences, save them, and access external booking sources.
\item Users can view destination-specific general health and safety information and complete a travel safety checklist.
\item For group trips, the trip creator can invite companions who can view and modify the shared itinerary.
\end{enumerate}

\subsection{Operational constraints for an educational travel-planning setting}
\begin{itemize}
\item Keep the solution usable on low-to-mid range devices via responsive web design.
\item Avoid dependence on advanced research algorithms; focus on workflow, practical AI integration, automation, and system correctness.
\item Design external API integrations as modular services so that individual service failures do not affect the entire application.
\item Provide stay recommendations rather than directly handling hotel bookings or payments.
\item Present health and safety information as general travel guidance and not as medical diagnosis or treatment recommendations.
\item Keep AI-generated itineraries editable by users rather than treating them as authoritative or final plans.
\item Keep collaborative planning to shared trips and shared itinerary editing in the initial scope; real-time synchronization is not required for the first implementation.
\end{itemize}

\section{Solution Approach \BvrHint{\ldots Engineering focus}}
This is an engineering course project, so we focus on building a reliable integrated travel-planning workflow rather than developing a novel AI model. The system will combine conventional software engineering techniques with existing AI and external information services.

\subsection{AI-powered itinerary generation \BvrHint{\ldots practical AI integration}}
The itinerary generation module will use an existing large language model/API rather than training a new foundation model.

The backend will provide the AI component with:
\begin{itemize}
\item Destination
\item Travel dates and duration
\item Budget
\item Interests
\item Travel style
\item Number of travellers
\item Weather information
\item Relevant activities and places
\end{itemize}

The AI will return a structured itinerary containing activities, approximate timings, locations, and other relevant information. The generated itinerary will be displayed by the frontend and remain editable by the user.

The same mechanism can support targeted modification requests such as ``Make Day 2 less hectic'' or ``Add more indoor activities.'' The AI will operate as a component of the application rather than as an independent chatbot.

\subsection{Recommendation and contextual assistance \BvrHint{\ldots non-research}}
The recommendation components will use external APIs and rule-based filtering where appropriate:
\begin{itemize}
\item Weather data will influence packing recommendations and travel-suitability information.
\item Trip duration will influence the quantity and type of packing items.
\item Planned activities will influence required clothing and equipment.
\item User budget, rating, type, and location preferences will filter accommodation recommendations.
\item Map and location information will support itinerary visualization and adding places to the trip.
\item Destination-specific health and safety information will be presented as general travel guidance.
\end{itemize}

The objective is to provide context-aware recommendations without claiming state-of-the-art recommendation research.

\subsection{Web architecture \BvrHint{\ldots web-based solution}}
A typical 3-tier web architecture:
\begin{itemize}
\item \textbf{Frontend:} responsive UI for trip creation, itinerary management, maps, packing lists, stay recommendations, safety information, collaboration, and saved trips.
\item \textbf{Backend API:} authentication, trip management, itinerary management, AI integration, weather integration, recommendation logic, collaboration, and external API communication.
\item \textbf{Database:} store users, trips, itineraries, activities, trip members, packing items, saved stays/places, and related trip data.
\end{itemize}

External services will be accessed through backend service modules rather than directly exposing API credentials to the frontend.

\subsection{CI/CD and fast delivery enabler}
CI/CD will be used to:
\begin{itemize}
\item Automatically build and run tests on every change.
\item Produce repeatable deployment artifacts to staging.
\item Enable safe and frequent releases of incremental features.
\end{itemize}

\section{Evaluation Criterion \BvrHint{\ldots measurable and attributable}}
We define success using measurable metrics tied to the core travel-planning workflow.

\subsection{Primary evaluation metric}
\textbf{Time-to-itinerary (TTI):} time between the user submitting their trip requirements and receiving the first usable generated itinerary.
\begin{itemize}
\item \textbf{Target:} median TTI $\leq$ 60 seconds during pilot window.
\item \textbf{Attribution:} measured from application timestamps between trip submission and successful itinerary generation.
\end{itemize}

\subsection{Secondary evaluation metrics}
\begin{itemize}
\item \textbf{Planning effort reduction:} reduction in the number of separate sources/applications users need to consult while creating a trip compared with their normal planning process.
\item \textbf{Itinerary usefulness:} user rating of generated itineraries on a simple 1--5 scale.
\item \textbf{Packing relevance:} percentage of generated packing items users consider relevant, measured through a short planning survey.
\item \textbf{Itinerary modification rate:} percentage of generated activities that users retain, modify, or remove.
\item \textbf{Collaboration usefulness:} user rating of the shared trip and itinerary-editing functionality on a 1--5 scale.
\item \textbf{Reliability:} availability of core functionality such as login, trip creation, itinerary access, and packing lists during the pilot.
\end{itemize}

\subsection{Pilot validation plan \BvrHint{\ldots high-level}}
\begin{itemize}
\item Recruit 10--20 pilot users as student travellers.
\item Ask users to create a sample trip using both their usual planning approach and TripWise.
\item Compare the time required to produce an initial itinerary.
\item Collect 1--5 ratings for itinerary usefulness, packing relevance, and overall planning experience.
\item Conduct a small group-trip test to evaluate shared trip and itinerary-editing functionality.
\item Use application logs to measure system response times and workflow completion.
\end{itemize}

\section{Scalability \BvrHint{\ldots with foresight}}
The proposition should scale in both theoretical and practical senses.

\begin{enumerate}
\item \textbf{Scalable (theoretically):} The system should support growth in number of trips and concurrent usage by:
\begin{itemize}
\item decoupling components (frontend/backend),
\item enabling pagination and indexing for common queries,
\item using stateless API design,
\item separating external API integrations into independent services.
\end{itemize}

\item \textbf{Operationally deployable (practically):} The system should run on common web hosting:
\begin{itemize}
\item managed database,
\item containerized or platform-hosted deployment,
\item environment-based configuration for API credentials,
\item CI/CD pipeline for staging/production.
\end{itemize}
\end{enumerate}

\section{Engine availability heuristic}
A mature set of ``engines'' (tooling/services) is available to implement this as a web-based project:
\begin{itemize}
\item Web framework for responsive frontend development and REST APIs.
\item Managed relational database.
\item Authentication approach (token-based or session-based).
\item Existing LLM/API for itinerary generation.
\item Weather API.
\item Maps and places API.
\item External accommodation/recommendation sources.
\item Test framework for unit/integration tests.
\item CI runner and staging deployment target.
\end{itemize}

We will use these mature components to focus on workflow design, practical AI integration, correctness, usability, and measurement rather than inventing new infrastructure or foundation AI models.

\section{Risks and mitigations}
\begin{itemize}
\item \textbf{External API availability:} weather, maps, places, or accommodation APIs may have rate limits or temporary failures. Use modular service layers, caching where appropriate, and fallback handling.
\item \textbf{AI-generated information:} AI may generate inaccurate or unsuitable recommendations. Present generated itineraries as recommendations, validate structured outputs, and allow users to edit them.
\item \textbf{AI response latency:} itinerary-generation requests may take time. Display generation status and measure response time during evaluation.
\item \textbf{Data privacy / consent:} minimize collection of personal information and store only data required for trip planning and collaboration.
\item \textbf{Recommendation quality:} generic or unsuitable recommendations may reduce user trust. Collect user feedback and allow manual editing rather than forcing AI-generated decisions.
\item \textbf{Collaboration complexity:} shared itinerary editing can increase implementation complexity. Start with shared trips and basic add/edit functionality; real-time synchronization is not required in the initial implementation.
\item \textbf{Evaluation measurement ambiguity:} instrument timestamps and define clear measurement procedures for time-to-itinerary and user usefulness ratings before development begins.
\item \textbf{Operational issues in pilot:} use staging early and ensure CI/CD produces repeatable deployments.
\end{itemize}

\section{Summary}
This project proposes a deployable web platform, \textbf{ItiNova}, designed to reduce the time and effort required for personalized travel planning. It integrates a core trip planner with AI-powered itinerary generation, weather and best-time recommendations, smart packing assistance, stay recommendations, an interactive travel map, travel health and safety information, and collaborative trip planning.

It meets the course criteria by emphasizing time-to-value through rapid iterations, implementing CI/CD to support frequent safe releases, and using measurable evaluation criteria (especially time-to-itinerary). It remains focused on engineering an integrated and usable travel-planning workflow rather than research-driven novelty.
